# SyncMaterial UI 设计方案

> **关联计划**: `.sisyphus/plan/team-collaboration.md`
> **最后更新**: 2025-05-20 (Phase 2 备货区 UI 设计、Phase 3 悬停提示设计定稿)
> **设计原则**: 协作式认领 + 共享进度 + 分段贡献显示

---

## 一、概述

本 UI 方案基于**协作式认领**模型设计。核心变化：
1. 不再有"认领数量"的概念，认领 = 加入协作组
2. 进度是公共的 = 备货区 + ∑(参与者背包)
3. 进度条用不同颜色段展示各贡献来源
4. 删除数量输入对话框，改为"一键加入"

## 三、进度条分段设计

### 3.1 三种状态

#### 状态 1: 未认领

```
┌──────────────────────────────────────────────────────────┐
│░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
└──────────────────────────────────────────────────────────┘
  未认领
```

- 进度条为空（灰色虚线或浅灰填充）
- 下方显示"未认领"文字
- 按钮显示 `[加入协作]`

#### 状态 2: 协作中（备货区有物品）

```
┌──────────────────────────────────────────────────────────┐
│██████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
└──────────────────────────────────────────────────────────┘
  备货区: 5  |  剩余: 59
```

- 已收集部分用橙色填充（备货区）
- 剩余部分为灰色
- 下方显示各段数量

#### 状态 3: 协作中（多人参与）

```
┌──────────────────────────────────────────────────────────────────┐
│██████████████████████████████████████████████████████████░░░░░░░░│
│  备货区    玩家A        玩家B        玩家C         剩余          │
│   5         30           12           10           7            │
└──────────────────────────────────────────────────────────────────┘
  备货区: 5 | 玩家A: 30 | 玩家B: 12 | 玩家C: 10 | 剩余: 7
```

- 每个参与者的贡献用不同颜色段显示
- 段宽度与数量成正比
- 下方显示详细数量（玩家名 + 数量）

#### 状态 4: 已完成

```
┌──────────────────────────────────────────────────────────┐
│██████████████████████████████████████████████████████████│
└──────────────────────────────────────────────────────────┘
  已完成 ✓
```

- 进度条满，深绿色
- 下方显示"已完成"
- 按钮显示 `[已完成 ✓]`（不可点击）

### 3.2 颜色方案

```java
// 进度条分段颜色
COLOR_STAGING   = 0xFFFFAA00;   // 橙色 - 备货区
COLOR_PLAYER_1  = 0xFF00AA00;   // 绿色 - 玩家1（自己）
COLOR_PLAYER_2  = 0xFF0000AA;   // 蓝色 - 玩家2
COLOR_PLAYER_3  = 0xFFAA00AA;   // 紫色 - 玩家3
COLOR_PLAYER_4  = 0xFF00AAAA;   // 青色 - 玩家4
COLOR_PLAYER_5  = 0xFFAA5500;   // 棕色 - 玩家5
COLOR_REMAINING = 0xFF444444;   // 深灰 - 剩余
COLOR_COMPLETED = 0xFF006600;   // 深绿 - 已完成
COLOR_UNCLAIMED = 0xFF333333;   // 浅灰 - 未认领（虚线）
```

**玩家颜色分配规则**：
- 当前玩家始终用绿色（COLOR_PLAYER_1）
- 其他玩家按加入顺序分配颜色
- 超过 5 个参与者时，第 6 个及以后合并为"其他"段（用灰色）

### 3.3 分段宽度计算

```
总宽度 = 进度条像素宽度（如 300px）
每段宽度 = (段数量 / 总需求) * 总宽度
最小段宽度 = 10px（防止数量太少时看不见）
```

### 3.4 悬停提示

鼠标悬停在进度条某段上时，显示 Tooltip：

```
┌─────────────────────┐
│ 备货区               │
│ 数量: 320           │
│ 占比: 15.6%         │
└─────────────────────┘

┌─────────────────────┐
│ 玩家A (Magic_red)   │
│ 背包数量: 128       │
│ 占比: 6.3%          │
│ 状态: 在线          │
└─────────────────────┘
```

## 五、备货区配置 UI（Phase 2）

### 5.1 入口

在 `GuiMaterialList` 顶部按钮栏增加 **"备货区配置"** 按钮。
- 仅负责人可见（后续 Phase 4 权限控制）
- 点击后打开 `GuiStagingAreaEditor`

### 5.2 备货区编辑器

类似 Litematica `GuiAreaSelectionEditorNormal` 的界面：

```
┌──────────────────────────────────────────────────────────┐
│  备货区配置                                  [×] 关闭     │
├──────────────────────────────────────────────────────────┤
│  当前原理图: my_building.litematic                        │
│                                                          │
│  备货区列表:                          [从选区添加]        │
│  ┌────────────────────────────────────────────────────┐  │
│  │ ☑ 仓库A  (x:100~120, y:64~70, z:200~215)    [删除] │  │
│  │ ☑ 仓库B  (x:150~165, y:64~70, z:200~210)    [删除] │  │
│  │ ☐ [新建备货区...]                            [删除] │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  提示: 使用 Litematica 小木棍框选区域后，点击"从选区添加" │
│        将当前选区添加为备货区。                            │
│                                                          │
│  [保存到服务器]  [取消]                                  │
└──────────────────────────────────────────────────────────┘
```

**交互逻辑**：
1. 打开时从服务端获取当前原理图的所有备货区列表
2. 点击"从选区添加"：通过反射读取 Litematica 当前选区的子区域，添加到列表
3. 点击"删除"：从列表移除（需点击"保存到服务器"才生效）
4. 点击"保存到服务器"：发送 `StagingAreaConfigC2SPacket` 到服务端
5. 点击"取消"：关闭界面，不保存

**数据结构**（客户端内存中）：
```java
public class StagingAreaRegion {
    String name;          // 备货区名称
    BlockPos pos1;        // 角点1
    BlockPos pos2;        // 角点2
    boolean enabled;      // 是否启用
}
```

## 十一、设计决策记录

### 11.1 为什么删除数量输入？

协作模型下，玩家不是"认领固定数量"，而是"加入收集组"。数量输入与协作理念矛盾，且会导致归属问题。

### 11.2 为什么进度条要分段？

- 让玩家直观看到各来源的贡献
- 激励参与（看到自己的贡献段增长）
- 方便负责人了解收集进度分布

### 11.3 为什么限制显示 5 个玩家？

- 进度条空间有限，玩家太多会导致段太窄看不清
- 超过 5 个时合并为"其他"段，保持 UI 简洁
- 悬停 Tooltip 可查看完整列表

### 11.4 为什么当前玩家始终用绿色？

- 快速识别自己的贡献
- 与其他玩家区分
- 符合"绿色=自己"的直觉
