# UI 重构设计草案：原生生态一致版

> 2026-11-18：用户接受当前原生生态一致版主清单方向并授权推进，随后批准 WP6／WP7＋主清单生产重构实施计划。首版 HTML 已停止打磨；标准 MaLiLib 控件、八列／来源进度与宽窄布局作为生产实现基线，诊断草图不直接合并。
>
> 当前实现为 beta.59／协议 5／schema 3，默认 legacy；本地完整验收及实现提交 `3653033` 的CI全部8项均通过，未打发布tag或部署正式服。

## 1. 用户已经确认的边界

- 可以完整重构界面，但新版至少要比原版更好，不能仅仅不同。
- 原型用于快速看布局，不精心打磨 HTML 或堆模拟功能。
- 材料清单始终是**团队收集总览**。开启取货指示器不改变表格口径；HUD／高亮负责个人辅助。
- 区域／仓库编辑**保留自动保存**，不增加“草稿 → 保存／取消”步骤。返回／Esc 不撤销已经保存的修改；准星选区维持原来的确认方式。
- 区域／仓库 CRUD 全员开放；同项目物理库存只计一次，备货区优先。不给参与者自动分配物品配额，不新增跨项目预留。
- SyncMaterial 是 Litematica／Syncmatica 的附属模组，界面应沿用该生态的控件、字号和操作习惯；可以重新组织布局，不意味着另外设计一套网页式皮肤。
- 已批准的具体实施范围见 WP6／WP7＋生产主清单计划；该授权不包括更换 UI 库、切默认后端、正式服发布或未经实机核对的最终视觉验收。

## 2. 原稿的问题与本次纠正

首版 HTML 在没有先看真实游戏界面的情况下，建议默认合并本人／他人背包列、移除行内进度、将负责人管理移到独立页，并制作了过重的模拟交互。源码阅读与网页测试不能证明这些变化比原版好。

这几项不再作为默认改版方案：

| 原稿候选 | 现在的处理 |
|---|---|
| 默认把本人／他人背包合成参与者持有 | 保留可横向比较的两列；没有空间证据时不先隐藏常用信息 |
| 移除常驻行内来源进度 | 保留来源分布与行内阶段提示，改善裁剪、颜色和文案 |
| 负责人操作全部移到团队页 | 保留当前界面内的快捷操作；独立团队详情不能成为常用操作的必经步骤 |
| 先进入批量模式才显示勾选 | 不作为默认；保留选中材料后直接分配／移除的短路径 |
| 常驻详情面板替代表格 | 详情可补充，但不能为了查看基本数量再多点一次 |
| HTML 功能和测试全绿说明布局更好 | 停止该论证；采用同数据、同逻辑尺寸的真实新旧截图 |

允许完全改版不等于必须丢弃旧界面的优点，也不等于只能几个最小修补。推荐按业务状态与布局职责重构，同时保留有用的信息和操作。

## 3. 已核查的真实基线

### 实际依赖

- Minecraft 1.21.7／1.21.8：MaLiLib **0.25.7**。
- Minecraft 26.2：MaLiLib **0.29.4**。
- 已核对仓库依赖声明、现有本地 jar 元数据和对应 API；0.25.7 有版本匹配的本地源码，0.29.4 仅核对了二进制接口，未声称读过完整实现。
- `GuiListBase.resize` 已向列表转发 resize，不能因项目 screen 没有重写就断言不会重排。
- MaLiLib 控件需要组合布局；渲染／输入签名在两个节点组不同，不能将网页 CSS 断点当游戏布局能力。

### 实机观察范围

在独立本地持久副本中启动 **Minecraft 1.21.8＋MaLiLib 0.25.7**，渲染当前 beta.58 的生产 `GuiMaterialList`。使用 12 种材料的合成数量、真实 Minecraft 物品图标与中文字体。

- 数量通过现有客户端状态入口注入；这是布局观察，不是完整服务端库存／协议闭环。
- 覆盖负责人／普通玩家、1920×1080 scale 2、1440×900 scale 2、1920×1080 scale 3，以及警告和勾选状态。
- 首轮诊断夹具编译失败于未捕获 SQLException；仅修夹具后运行成功。
- 首轮截图存在资源加载画面／原版通知遮挡；已保存历史证据，增加加载完成等待并清理测试通知后重新捕获。
- 生产 `src/main`、`shared/src/main` 和根版本文件与副本基线逐文件 hash 相同。截图夹具和候选都只存在于诊断副本的测试源集。

### Litematica／Syncmatica 的真实上游对照

本轮实际加载版本为 **Minecraft 1.21.8、Litematica 0.23.7、Syncmatica 0.3.15、MaLiLib 0.25.7**，版本来自最终客户端日志，不用下载页的最新版本替代运行时事实。

已捕获上游自己的 screen，而非照着源码仿画：

| 界面 | 观察内容 |
|---|---|
| Litematica 主菜单 | 原版按钮纹理、字号、开关文字及页面返回习惯 |
| Litematica 材料列表，960×540／720×450 | 可排序表头、交替行、行内动作、标准滚动条与底部汇总 |
| Litematica 放置配置，720×450 | 左侧子区域列表、右侧就地属性／操作、名称与坐标编辑 |
| Syncmatica 共享列表及选中详情，720×450 | 行内下载／材料清单／移除按钮、右侧信息栏、选中行高亮 |

这些截图使用上游真实绘制代码与合成材料／放置条目。Syncmatica 在诊断环境没有现成客户端 context，夹具建立无网络 `Context` 后在结束时清理／恢复；没有下载、保存原理图、移除真实共享项目或连接正式服务器。因此可作为视觉与布局依据，不能证明上游完整联网／权限状态。详情中的原理图数据版本也是夹具值，不是当前 Minecraft 运行时版本。

设计判断是：**沿用控件语言，不照抄所有布局。** 上游顶部也有成排按钮，但这不要求 SyncMaterial 继续把全部功能堆在同一行。标准按钮纹理、红绿开关文字、普通字号、列表与就地操作值得延续；高频材料筛选、个人显示开关和低频角色管理仍按本模组的使用任务组织。

### 旧界面值得保留的部分

- 八列：物品、总数、缺口、本人背包、其他背包、备货区、仓库、认领者。
- 行内来源分段进度和悬停数量解释；不需要逐项打开详情才能比较。
- 行内认领／退出，负责人勾选后直接分配／踢出。
- 负责人侧栏与材料表可同时查看，不强迫页面往返。
- Minecraft 风格与现有 MaLiLib 的操作习惯。

### 已看到的具体问题

- 720×450／640×360 逻辑窗口中，认领者文字会挤到行按钮附近，部分缩放会越进侧栏；已有空间分配需要重构，而不是简单固定列间距。
- 新鲜度与重叠警告绘制在固定位置，警告出现时会覆盖表头。
- “已完成”使用团队收集总量判断，不能表示物品已送达备货区。
- 这些截图只证明上述场景；长名字、更多参与者、8 语言与 26.2 实际行为仍待验证。

## 4. 当前原生布局候选：生态一致、舒服使用优先

**2026-11-18 已接受的设计基线，后续生产迭代仍需实机验收。** 用户允许助手自行查看实际截图、继续迭代或重新开始，并明确不必刻意分区；生产版保留标准 MaLiLib 控件，不再使用自绘按钮皮肤。下列诊断阶段记录是设计依据，不代替 beta.59 生产验收。

- 上方标题／状态保持简短。搜索有明确提示，全部／我参与／待收集为轻量筛选；表头可直接排序，不将它们画成同样醒目的大按钮。
- 区域／仓库和刷新直接可达。个人 HUD／取货／线框开关放在底栏，使用 `ButtonOnOff` 的标准红绿开关文字，不采用网页式滑块。
- 表格保留八列、右对齐数量、行内来源进度和参与者信息；分段进度线止于操作区之前。认领／退出使用标准 `ButtonGeneric`，仍是一步入口。
- 宽窗口保留团队侧栏。较窄窗口用就地团队浮层查看角色；勾选后的分配／移除直接出现在底栏，无须先进入“批量模式”或团队页。
- 普通窄屏优先复用底栏空间；实际本地化文本放不下时批量动作另占一行，并同步减少表格可用高度。不得为保持行数而让控件相互覆盖或缩小字号。
- 使用 `GuiScrollBar`、`GuiTextFieldGeneric`、MaLiLib 的边框与列表高亮。筛选／表头只关闭标准按钮背景并作选中提示，没有自绘按钮皮肤子类；勾选框与来源进度仍是本模组绘制内容。
- 不以区域数量或与旧版的差异大小评判设计，按扫读、操作距离、信息完整和真实缩放判断。

```text
项目标题                                      材料凑齐 N／总种数
团队收集总览 · 取货指示仅作用于个人
搜索材料 / ID   全部  我参与  待收集       [团队]  区域与仓库  刷新

物品   需求   还需收集   我的背包   其他背包   备货区   仓库   参与者  认领/退出
       └────────── 行内来源进度与阶段说明 ──────────┘

HUD开关  取货开关  线框开关          已选N  分配  移除  清空  返回
```

宽屏角色信息在侧栏；`[团队]` 和批量底栏示意的是窄屏负责人场景，不是同一尺寸同时出现全部控件。

### 实际自查与迭代

1. 前轮原生草图发现刷新符号不清楚、批量工具条挤掉一行、来源进度碰到行按钮。改为“刷新”文字、复用底栏、限制来源进度边界。
2. 实际鼠标核对发现团队浮层点击穿透；改为浮层独占点击，外部点击只关闭浮层，不继续触发行按钮。当前实现也提供 Esc 关闭，最终输入用例只实际断言了外部点击关闭，未把 Esc 计入已运行覆盖。
3. 用户提出附属模组生态一致性后，捕获上游真实界面；撤掉前稿 `ComfortButton` 自绘皮肤，采用标准 `ButtonGeneric`／`ButtonOnOff`／`GuiScrollBar`，再运行全部布局场景。
4. 上游截图首轮因 Syncmatica 客户端 context 缺失而超时；夹具改为无网络 context。选中态首次编译因 `getListWidget()` 为 protected 失败，改为真实鼠标选中。失败记录保留，未修改生产代码或放宽成功条件。
5. 最终一轮实际 `START 16:25:06 → PASS 16:25:29`，Gradle `BUILD SUCCESSFUL in 38s`。重新核对工作区及受测副本的 228 份生产／构建受控文件，均与基线相同；仅忽略并记录系统 `.DS_Store` 元数据，不删额外文件。

### 有证据的收益与取舍

| 同一合成数据的观察尺寸 | 旧版完整材料行 | 当前草图完整材料行 | 团队与批量操作 |
|---|---:|---:|---|
| 1920×1080／scale 2 → 960×540 | 12 | 12 | 侧栏显示；勾选后动作可用 |
| 1440×900／scale 2 → 720×450 | 10 | 10 | 团队浮层；批量动作在底栏，勾选不减行 |
| 1920×1080／scale 3 → 640×360 | 7 | 7 | 团队浮层；批量动作在底栏，勾选不减行 |

- 八列和常驻行内来源没有删除；所测窄窗口参与者文字裁剪在数据区内，不再挤进侧栏或行按钮。
- “材料已凑齐”与“备货区已备齐”分开；过期时用独立横幅和“准备待确认”，不覆盖表头，也不将上次数量标成已确认完成。
- 标准游戏字号未缩小，行距由 34 改为 32 逻辑像素。普通玩家720×450仍为10行；前稿曾为11行，本轮保留标题／工具留白，不追求所有尺寸的最大密度。
- 控件纹理、开关文字和滚动条与上游一致；不需要为了改布局换 UI 库。
- 窄窗口低频角色操作比常驻侧栏多一次打开，且浮层暂时遮挡表格右上方；换取正常浏览时的表格宽度。批量分配／移除不需要打开该浮层。
- 生态一致版沿用半透明背景，世界与原版／模组 HUD 在部分区域仍会透出，不能沿用前稿“完全不透明”的描述。正式实现应再核对不同世界背景及浮层层级；视觉一致不等于必须保留影响阅读的透出。
- 保留来源说明有助于扫读，但也重复部分表格数量；过期场景逐行提示较多。该信息层级是当前候选的明确取舍，不用自动化通过替代舒适度判断。
- 助手推荐这一稿作为下一阶段设计基线；**这是设计判断，不代替用户接受，也不意味着整体重构完成。**

## 5. 保持清楚的业务含义

记需求 N、备货区 S、仓库 W、全体参与者有效持有 P、本人当前持有 M。

| 表达 | 含义 |
|---|---|
| 团队还需收集 | `max(0, N-S-W-P)`，不是个人配额 |
| 材料已凑齐 | 当前可信观测下团队缺口为 0，不表示建筑完成 |
| 备货区尚缺 | `max(0, N-S)`，不是都要从仓库再拿一遍 |
| 备货区已备齐 | 已配置备货区且当前可信观测足量 |
| 本人当前可取 | `max(0, min(N-S-M, W))`，只指示本人参与材料，不减队友、不自动预留 |

- 没有备货区显示“未配置”；空目录显示“暂无需求”，不是“全部建筑完成”。
- 未知／过期显示最近数量和警告，不能把 0 或满进度当确认完成。
- 新鲜度只有项目级证据时就显示项目级警告，不编造每材料／每容器的精确状态。
- 兼容统计仍可用，但不冒充 Foundation 完整覆盖证明。
- 本人即时背包（取货包含光标持物）与服务器计入量分开；本机刷新不能覆写团队缺口。
- HUD 也区分：没有参与、本人无需再取、仓库无货但团队仍缺、材料由队友持有、备货已齐、数据待确认。
- 隐藏 HUD 或关闭 GUI 不停止数据流；高亮仅辅助，不自动取物／导航／加载区块。

## 6. 后续重构的职责与检查标准

```text
共享业务快照
  → 客户端项目状态（连接、目录、兴趣、可信数据）
  → 纯视图模型（表格／来源进度／个人 HUD）
```
