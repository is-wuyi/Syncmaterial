## 2. 状态与维护规则

- `✅ 已完成`：约定交付已实现，相关验收通过；实现批次同时记录提交、推送和 CI 状态。
- `◐ 部分完成`：已有可复用实现，但该项终态仍有缺口。子任务使用复选框标明，不以一个勾代表全部完成。
- `▶ 进行中`：已经实际启动的设计或实现；只推荐、尚未启动的下一批不能标进行中。
- `⬜ 未开始`：尚未实施，或仍需设计后再执行。
- `⛔ 阻塞`：必须写明具体阻塞、影响范围、解除条件和负责处理的一方。

**更新时机**：开始新批次、确认重要决策、改变实施边界、完成验收、提交／推送及确认 CI 后同步更新。阶段结束后将“下一批”移动到实际下一项。

**证据纪律**：

1. 实现、验证、提交、推送、CI 分别记录；待运行、失败、跳过、缺证据都不能写成通过。
2. 引用旧验收时注明所属提交，不将旧日志冒充当前源码结果；专题文档的历史表保留原日期和口径。
3. 建议、技术默认和用户已确认决策分开；需要改变产品语义时先确认，不用助手推断替代用户定案。
4. 按交付与行为覆盖跟踪进度，不按提交数、代码行数或随意百分比估算。
5. 全仓终态验收保留覆盖清单：主线程阅读、代理阅读、片段核对、未覆盖及动态未验证项如实区分。
6. 主线程优先在工作区编辑；本机构建使用本地持久副本。代理并行使用独立副本，及时受控合并，不在同一 Stonecutter 工作树并发切版本。未提交源码不得只有 `/tmp` 副本。
7. 本文件保留简短里程碑和有效决策，不堆聊天流水账、完整日志、凭据或用户设计资料。

## 4. 下一批规划：负责人管理＋批量协作

**状态：待具体设计，尚未开始编码。** 本节是下一步建议与边界，不是提前批准所有实现细节。

### 交付目标

- 让 Foundation 的四组占位能力变为真实可用：负责人操作、批量分配、踢人、玩家目录。
- 将角色／协作写操作放进共享业务与仓储，Minecraft 适配只负责玩家解析和网络接线。
- 复用现有管理界面和已发布请求／响应；不通过调用旧 `Phase4Handler` 伪装完成迁移。

### 必须保持

- 主／副负责人权限规则和离线分配行为，不顺手给全员开放的区域 CRUD 添加权限。
- 材料 ID、认领、区域配置与仓库引用不因角色修改或重导入意外丢失。
- 批量操作与踢人的失败／事务语义需要明确，并保持现有用户可见功能。
- Hello 与已发布包字段冻结；新增能力若有真实语义变化，先设计双端能力门。
- 默认 legacy、Foundation 独立新库、旧库只备份；不同时做 GUI 改版、发布或正式服切换。

### 放行条件

1. 共享真实 JDBC 测试：角色写事务、权限与身份升级、重导入保留、批量／踢人和库存清理。
2. 网络回归：未握手、越权、非法／跨项目材料、空目标、过期快照、断线与广播一致性。
3. 三节点真实服务端和管理 GUI 操作／回包闭环；不将旧后端单测当作 Foundation 已接通。
4. 完整聚合验收、无新增静态告警、中文提交推送及 CI 通过。
